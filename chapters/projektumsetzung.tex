\section{Übersetzten des Google V8 C++ Quellcodes}

Dieser Abschnitt beschreibt wie die Google V8 Quellcode in eine statische Bibliothek übersetzt werden kann.

\subsection{Linux}

Aufgrund der Compilervorgaben von WinCC OA gestaltet sich die Übersetzung des Quellcodes auf Linux schwierig. 
Das Google V8 Buildsystem ist auf Debian-Basierende Distributionen ausgelegt, das bedeutet die Engine kann auf dem Zielsystem
SUSE Linux Enterprise 12.5 nicht übersetzt werden. Ein alternativsystem mit der passenden Compilerversion stellt Ubuntu 18.04
zur Verfügung.

\begin{program}[h]
\caption{Installation von GCC-4.8.5 auf Ubuntu 18.04}
\label{src:inst_gcc}
\begin{GenericCode}
$ sudo apt update
$ sudo apt upgrade
$ sudo apt install git libglib2.0-dev python g++-4.8 gcc-4.8
$ sudo update-alternatives --install /usr/bin/gcc gcc /usr/bin/gcc-4.8 10
$ sudo update-alternatives --install /usr/bin/g++ g++ /usr/bin/g++-4.8 10
\end{GenericCode}
\end{program}

In dem Beispiel \ref{src:inst_gcc} ist gezeigt wie man auf einem Ubutu 18.04 System den benötigten Compiler nachinstallieren und als
Standardoption zum Übersetzten von Quellcode konfigurieren kann. Hat man diese Schritte durchgeführt, kann man die Google V8-Engine mit dem in Anhang 
\ref{app:v8build} gezeigten Skript kompilieren. Dabei werden zuerst automatisch der Quellcode und alle benötigten Dateien aus dem Google-Versionskontrollsystem 
bezogen. Als Nächstes wird eine Buildkonfiguration erzeugt. In dieser wird das Buildsystem angewiesen eine statische
Bibliothek zu generieren. Danach erfolgt eine Nachbearbeitung der generierten Dateien, weil die Standardkonfiguration einen neueren Compiler
voraussetzt. Hierbei wird die \textit{-std=gnu++14} Anweisung durch \textit{-std=gnu++11} ersetzt. Letztendlich wird der Buildprozess 
gestartet. Die fertigen Kompilate sind unter \textit{v8} und die Headerdateien unter \textit{include} zu finden und können auf einem SUSE Linux Enterprise 12.5
System verwendet werden. 

\subsection{Windows}

Auf Windows gestaltet sich dieser Prozess deutlich einfacher. Hier ist es zunächst nötig, Visual Studio 2015 zu installiert. Dadurch wird das \textit{Visual Studio Toolset} v140
zur Verfügung gestellt. Im nächsten Schritt muss man das in \ref{app:v8build} gezeigte Powershell-Skript für Windows mit folgendem Kommandozeilenparameter ausführen: 

\begin{GenericCode}[numbers=none]
$ powershell.exe -noprofile -executionpolicy bypass -file .\build_windows.ps1
\end{GenericCode}

Dadurch wird ähnlich wie unter Linux der Quellcode und weitere Dateien aus dem Google-Versionskontrollsystem bezogen, die Konfigurationsdateien erzeugt
und der Kompilevorgang angestoßen. Die übersetzten Bibliotheksdateien und die dazugehörigen Headerdateien befinden sich danach unter \textit{v8} und \textit{include}.

\section{Implementierung der Programmbibliothek}

Nun, da erklärt wurde, wie man ein Kompilat der Google V8 Engine als statische Bibliothek erhält, kann die auf die Implementierung der 
Programmkomponente eingegangen werden. Hierbei werden die einzelnen Klassen anhand deren UML-Repräsentation (\textit{Unified Modeling Language}) 
beschrieben. Das gesamte UML-Diagramm mit allen Relationen kann in Anhang \ref{app:classdiag} eingesehen werden.

\subsection{Implementierung der Singleton Klasse}

\begin{figure}[h]
	\centering \includegraphics[width=0.63\textwidth]{singleton}
	\caption{Singleton Template-Klasse.}
	\label{fig:singleton}
\end{figure}

Diese in \ref{fig:singleton} gezeigte Template-Klasse implementiert eine wiederverwendbare Umsetzung des Singleton-Entwurfsmusters \cite{Singleton}. Ableitende Klassen erhalten indem sie
sich selbst als Template-Parameter übergeben eine \textit{GetInstance()} Funktion, die die einzige Instanz als \textit{Shared-Pointer} zurückgibt. 
Dadurch ist ein korrektes Freigeben des Speichers am Ende der Programmausführung gewährleistet. Ableitende Klassen müssen zusätzlich deren 
Konstruktor als \textit{protected} deklarieren und die Singleton-Klasse als \textit{friend} hinzufügen. Die \textit{GetInstance()} Methode nimmt
jene Parameter entgegen, die eine ableitende Klasse zur Konstruktion benötigt.

\subsection{Implementierung der libV8 Klasse}

\begin{figure}[h]
	\centering \includegraphics[width=0.63\textwidth]{libv8}

Abbildung \ref{fig:libv8} zeigt die Hauptkomponente der Bibliothek. Diese Klasse verwaltet das \textit{Isolate} Objekt der Google V8-Engine und alle

als ersten Parameter einen Pfad zu einer Skriptdatei und als zweiten einen booleschen Wert der angibt ob der Ausführungskontext am Ende des Skriptes aufgeräumt 
werden soll oder nicht. Erstere verwendet immer dieselbe Ausführungsumgebung (m\_DefaultContext), dadurch ist es möglich eine Liste von Skripten auszuführen, 
die auf die gleichen Ressourcen Zugriff besitzen. Zweitere erstellt für jeden Aufruf ein eigenes \textit{Context}-Objekt und gibt eine Nummer zurück, die diesen Kontext identifiziert. 
Somit lassen sich mehrere Skripte unabhängig voneinander ausführen. Die Methoden \textit{RecreateDefaultContext()} und \textit{ForceDisposeContext()} erlauben ein späteres 
Aufräumen des Standardkontexts und der neu erstellten. Zweiterer muss man als Parameter die über \textit{ExecuteNew()} Identifikationsnummer der zu löschenden Ausführungsumgebung mitgeben.
Mit Hilfe der \textit{AddJSCommands()} Funktion kann man den Ausführungskontexten eigene Javascriptfunktionen zur Verfügung stellen. Über diesen Mechanismus ist ein dynamisches Erweitern möglich. Über diesen mechanismus ist ein dynamisches 
erweitern möglich. \textit{GetDebuggerInstance()} gibt ein abstraktes Observer-Objekt retour, das einer Websocket-Server Implementierung des \textit{SiPlant} Produktes übergeben werden kann.
Da innerhalb eines Programms nur eine einzige Google V8 Engine gestartet werden darf, leitet diese Klasse von der Singleton-Template-Klasse ab. Dadurch ist ein mehrfaches 
Instanziieren ausgeschlossen.

\subsection{Implementierung der SIS\_InspectorClient Klasse}

\begin{figure}[h]
	\centering \includegraphics[width=0.63\textwidth]{inspectorclient}
	\caption{SIS\_InspectorClient Klasse.}
	\label{fig:inspcl}
\end{figure}

Diese Klasse implementiert wie in Abbildung \ref{fig:inspcl} erkennbar drei Interfaces. Das \textit{AbstractJDataProvider}-Interface ist eine Observer-Klasse 
für den in dem \textit{SiPlant} Produkt verwendeten Websocket-Server. Werde Nachrichten erhalten, gibt der Server diese an die \textit{ExecuteCommand()} Methode weiter.
Der erste Parameter ist hierbei die Nachricht im JSON-Format und die zweite der Websocket-Endpunkt. Die Implementierung dieser Funktion gibt eine leere Struktur zurück,
dadurch sendet der Websocket-Server keine unmittelbare Antwort an den Client. Über das \textit{SIS\_IEndpoint} Objekt ist es später jederzeit möglich Nachrichten zu senden
darum wird es als Member-Variable gespeichert. Die \textit{GetWSClient()} Funktion ermöglicht späteren Zugriff auf diese.
Da man in der Regel nur ein \textit{Isolate} benötigt leutet diese Klasse ebenfalls von der Singleton-Template-Klasse ab. Dank der Geerbten \textit{GetInstance()} Funktion kann so 
das zu verwendende \textit{Isolate} Objekt an den geschützten Konstruktor übergeben werden. Dies geschieht beim Aufrufen der \textit{GetDebuggerInstance()} Methode des \textit{libV8}-Singletons automatisch.
Des Weiteren wird im Konstruktor ein \textit{V8Inspector}-Objekt mit einer Eigenen \textit{V8InspectorSession} erstellt. Dieser Session wiederum wird mit einer Instanz der \textit{SIS\_InspectorFrontend}
Klasse zum Senden von Antworten der V8-Engine ausgestattet. Über die \textit{AddContext()} und \textit{RemoveContext()} Funktionen kann man zu überwachende Ausführungsumgebungen hinzufügen und entfernen.
Schließt ein Websocket-Endpunkt die Verbindung, führt dies durch den Websocket-Server zu einer Ausführung der \textit{OnConnectionClosed()} Methode. In dieser wird die \textit{} Member-Variable auf nullptr gesetzt,
damit das \textit{SIS\_InspectorFrontend}-Objekt keine Antworten mehr sendet. Das \textit{v8InspectorClient} Interface schreibt die Umsetzung der \textit{runMessageLoopOnPause()} und \textit{quitMessageLoopOnPause()}
Methoden vor. Wird ein Javascript zum Beispiel wegen eines Breakpoints gestoppt, arbeitet die Erstere so lange alle Websocket-Nachrichten ab, bis die zweitere Funktion ausgeführt
wird um die Ausführung fortzusetzen.

\begin{figure}[h]
	\centering \includegraphics[width=0.63\textwidth]{inspectorfrontend}
	\caption{Implementierung des \textit{v8Inspector::Channel} Interfaces.}
	\label{fig:inspchan}

Die Google V8-Engine antwortet auf Debugging-Befehle über das \textit{v8Inspector::Channel} Interface. Um an die Browser-Entwicklungswerkzeuge Antworten 
antworten auf Analysebefehle Senden zu können wurde daher die in \ref{fig:inspchan} gezeigte Klasse umgesetzt. Der Konstruktor kann über eine Friend-Beziehung nur

\textit{ProcessAnswer()} ist eine Hilfsfunktion, die die Antworten der V8-Engine in normale Strings umwandelt.

\subsection{Implementierung der V8Context Klasse}

\begin{figure}[h]
	\centering \includegraphics[width=0.63\textwidth]{v8context}
	\caption{V8Context-Klasse, repäsentiert einen Ausführungskontext.}
	\label{fig:v8ctx}
\end{figure}

Die in Abbildung \ref{fig:v8ctx} gezeigte Klasse verwaltet einzelne Ausführungskontexte und ist somit für das Ausführen der Javascript-Dateien zuständig.
Um eine falsche Verwendung zu vermeiden, ist der Konstruktor nur von der \textit{libV8}-Klasse aufrufbar (Friend-Beziehung). Beim Erstellen einer \textit{V8Context}-Instanz wird
die Identifikationsnummer mitübergeben. Des Weiteren wird im Konstruktor die \textit{m\_AdditionalJSCommands} Variable mit Standartbefehlen für den Datenbankzugriff und die Alarmbehandlung befüllt.
Das \textit{libV8}-Singleton gibt die über \textit{ExecuteDefault()} oder \textit{ExecuteNew()} erhaltenen Dateipfade and die \textit{Execute()} Methode eines jeweiligen \textit{V8Context}-Objekts weiter. Bevor das Skript gestartet wird, 
übergibt die Klasse das \textit{Context}-Objekt an das \textit{SIS\_V8InspectorClient}-Singleton. Dadurch wird eine Überwachung der Ausführungsumgebung zur Fehleranalyse durch Browser-Entwicklungswerkzeuge ermöglicht.
Als nächstes werden die \textit{RegisterCommands()} und \textit{RegisterToGlobal()} Funktionen aller ICustomJSCommands Objekte der m\_AdditionalJSCommands Member-Variable aufgerufen. Wird der Ausführungskontext zerstört,
so werden im Destruktor alle \textit{FreeResources()} Methoden dieser Objekte aufgerufen und die Überwachung über die \textit{RemoveContext()} Funktion des \textit{SIS\_InspectorClient}-Singletons beendet.

\subsection{Implementierung des ICustomJSCommands Interface}

\begin{figure}[h]
	\centering \includegraphics[width=0.63\textwidth]{icustomjscommands}
	\caption{ICustomJSCommands-Interface zum erweitern des Javascript-Sprachumfangs.}
	\label{fig:customjs}
\end{figure}

Das Interface in der Grafik \ref{fig:customjs} erlaubt ein Erweitern des Javascript-Sprachumfangs. Konkretisierungen müssen drei Funktionen
implementieren, die von der \textit{V8Context}-Klasse aufgerufen werden. 

\begin{itemize}
	\item \textit{RegisterCommands()} ermöglicht das Hinzufügen von C++-Methoden zu dem \textit{ObjektTemplate}-Objekt bevor das \textit{Context}-Objekt erstellt wird.
	\item Nach Konstruieren des Ausführungskontexts, wird \textit{RegisterToGlobal()} aufgerufen. Dieser Funktion wird die auf Basis des \textit{ObjektTemplate}-Objekts erzeugte Instanz mitgegeben. Dadurch ist es über C++ möglich Javascript Methoden auszuführen und Variablen zu verändern.
	\item \textit{FreeResources()} wird beim Freigeben der Ausführungsumgebung aufgerufen um allokierte Ressourcen freigeben zu können.
\end{itemize}

\section{Implementierung des Agenten}

Der Agent verwendet die zuvor beschriebene Bibliothek, um Javascript-Dateien ausführen zu können. Die Datei ist über einen Kommandozeilenparameter 
übergebbar. In der Hauptfunktion ist am Anfang das Auslesen des Skriptpfades aus den übergebenen Parametern implementiert. Als Nächstes wird die Verbindung mit dem SCADA-System hergestellt. Darauf folgt das Starten des \textit{SiPlant} Websocket-Servers. Dieser erhält das von der \textit{GetDebuggerInstance()} Funktion zurückgegebenen Observer-Objekt. 
Dadurch ist ein Verbinden mit einer Browser-Entwicklerkonsole möglich. Danach wird vor der Hauptschleife mit dem wiederkehrenden 
\textit{dispatch()} Aufruf das übergebene Skript an die \textit{ExecuteDefault()} Funktion des texit{libV8()}-Singletons weitergereicht. 
Der boolesche Parameter ist hier auf 'false' gesetzt, da der Ausführungskontext nicht zerstört werden soll. Somit ist es möglich, 
eigene Algorithmen zu implementieren und eventorientiert Berechnungen in Javascript durchzuführen.
