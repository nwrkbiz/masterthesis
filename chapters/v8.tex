\chapter{Google V8 Javascriptengine}
\label{cha:v8engine}

Während im letzten Kapitel auf die Konzepte und Funktionsweise von SCADA-Systemen eingegangen wurde, widmet sich dieses nun der Skriptsprache Javascript. 
Es wird gezeigt, wie diese Sprache technisch funktioniert. Als Javascriptengine bezeichnet man Programmkomponenten, die ECMA standardkonformen Quellcode ausführen können \cite{ecma}. 
Danach werden die drei bekanntesten Engines verglichen, um zu erläutern, warum die Google-V8-Engine für die Umsetzung gewählt wurde. 
Im letzten Abschnitt werden die Konzepte, Funktionsweise und Programmierschnittstelle dieser beschrieben.

\section{Grundlagen}
\label{cha:Grundlagen}

Um zu verstehen, wie eine Javascriptengine funktioniert, müssen die Grundlagen der Compilertheorie umrissen werden. Dazu wird
hier nun Bezug auf \cite{dragonBook} und \cite{Terry1997CompilersAC} genommen.

\subsection{Sprachprozessoren}

\begin{figure}[h]
    \centering
    \subfloat[Compiler]{{\includegraphics[width=0.45\textwidth]{compiler} }}%
    \qquad
    \subfloat[Interpreter]{{\includegraphics[width=0.45\textwidth]{interpreter} }}%
    \caption{Diese Abbildung zeigt die Sprachprozessoren Compiler und Interpreter im Vergleich.}%
    \label{fig:compiler_interpreter}%
\end{figure}

Als Compiler bezeichnet man einen Sprachprozessor, der Quellcode von einer Sprache in eine andere übersetzt. In der Regel ist die Zielsprache
eine Sammlung von Instruktionen gebündelt in einer ausführbaren Datei. Diese kann wie in Abbildung \ref{fig:compiler_interpreter} links gezeigt 
gestartet werden, um Eingaben zu verarbeiten und Ausgaben zu generieren. Ein Interpreter ist ein anderer Typ von Sprachprozessor, der im Gegensatz 
zum Compiler keine Übersetzungen erzeugt, sondern den Quellcode direkt ausführt. Ein Beispiel dafür ist in der Grafik \ref{fig:compiler_interpreter} rechts illustriert. 
Für bestimmte Programmiersprachen wie Javascript sind auch Mischformen möglich. Beide Typen eint
die Eigenschaft, dass sie im ersten Schritt das Quellprogramm Analysieren müssen, um eine für sie verständliche Zwischensprache zu erzeugen. 
Diese Aufgabe übernimmt das \textit{Frontend}.

\subsection{Frontend}

Als Frontend wird in der Compilertheorie jene Komponente bezeichnet, die eine Programmiersprache in eine maschinenunabhängige 
Zwischendarstellung übersetzt.

\begin{figure}[h]
	\centering \includegraphics[width=0.70\textwidth]{frontend}
	\caption{Schritte des Frontends \cite{compilerFrontEnd}.}
	\label{fig:compiler_frontend}
\end{figure}

Wie in der Grafik \ref{fig:compiler_frontend} ersichtlich, werden dazu drei Schritte durchgeführt. Ziel ist es, einen abstrakten
Syntaxbaum zu erhalten, der für die spätere Codeerzeugung oder eine direkte Ausführung verwendet werden kann.

\subsubsection{Lexikalische Analyse}

Damit bezeichnet man das Einlesen eines Programmcodes, um die Zeichenketten in sinnvolle Sequenzen, sogenannte Lexeme, zu Gruppieren
und entsprechende Token zu erzeugen. Als Lexem wird eine einzelne sprachliche Bedeutungseinheit verstanden. 
Um Schlüsselworte, Operatoren und Symbole erkennen zu können, müssen dazu deterministische Automaten implementiert werden, die
Sprachmuster feststellen können. Auf Basis dieser Muster werden Token mit optionalen Attributen generiert, die an die syntaktische Analyse weitergegeben
werden. Lexikalische Analysatoren werden auch \textit{Lexer} oder \textit{Scanner} genannt. Die Symbole einer Sprache werden in 
diesem Prozess in einer eigenen Tabelle abgelegt, die später in der semantischen Analyse Verwendung findet. Besitzt ein Token
einen Attributwert, so verweist dieser auf ein Element in der sogenannten Symboltabelle.

\subsubsection{Syntaktische Analyse}

Die Syntaktik beschreibt Regeln, auch Grammatik genannt, nach denen Texte strukturiert werden. Aus diesem Grund wird
in dieser Phase aus den Token des \textit{Scanners}, wie in Abbildung \ref{fig:compiler_frontend} gezeigt, 
eine Baumstruktur erstellt, die den gammatikalischen Aufbau der Eingabe wiederspiegelt. 
Dies wird durch Parsen der Ausdrücke und Statements erreicht. Weicht das Quellprogramm von der Grammatik ab, so wird dies 
als Syntaxfehler erkannt. Diese Komponente wird auch \textit{Parser} genannt.

\subsubsection{Semantische Analyse}

Unter Semantik wird die Zuordnung von Bedeutung zu Texten verstanden. Daher wird in dieser Phase mithilfe des Syntaxbaumes und der
Symboltabelle die semantische Konsistenz des Programmes überprüft. Es werden Gültigkeitsbereiche verwaltet und die
Einhaltung von Kontextbedingungen verifiziert. Ist dies nicht der Fall, so wird ein semantischer Fehler erzeugt.
Falls die Sprachdefinition bestimmte Typkonvertierungen erlaubt, werden diese umgesetzt. Zum Beispiel kann ein binärer arithmetischer Operator 
entweder auf Ganzzahlen oder auf Gleitkommazahlen angewendet werden. Werden die Zahlentypen vermischt, kann der Compiler eine Umwandlung vornehmen.
In Abbildung \ref{fig:compiler_frontend} ist dies unter der Annahme, dass \textit{initial} und \textit{rate} Gleitkommazahlen repräsentierem
durch die eingefügte \textit{inttofloat} Operation erkennbar. 

\subsection{Umsetzung in Javascriptengines}

Die Javascriptengines Google V8, Mozilla Spidermonkey und Apple JavaScriptCore verwenden alle dasselbe Konzept \cite{jsSpiderMonkey}, \cite{jsCore}, \cite{v8ByteCode}.
Es wird zunächst über ein Frontend aus dem Javascript-Quellcode ein abstrakter Syntaxbaum erstellt. Dieser wird in eine Zwischensprache
mit den Namen \textit{Bytecode} übersetzt, die von einer virtuellen Maschine ausgeführt werden kann. Zur Laufzeit wird ermittelt, welche
Codesequenzen oft durchlaufen werden. Dieser sogenannte \textit{Hot-Code} wird unmittelbar (Just-In-Time) in echte Prozessorinstruktionen übersetzt, die dann direkt 
von dem Prozessor der Zielplattform ausgeführt werden können. Der generierte Maschinencode wird danach für eine spätere Ausführung in einem Cache abgelegt. 
Da Javascript eine dynamische Skriptsprache ohne Typsicherheit ist, kann es jedoch passieren, dass an eine optimierte Funktion ein 
Datentyp übergeben wird, der von dieser nicht verwendet werden kann. Tritt dieser Fall ein, muss auf den \textit{Bytecode} zurückgegriffen werden.

\begin{program}[h]
	\caption{Deoptimierung in Javascript.}
	\label{prog:js_deopt}
	\begin{GenericCode}
// Testfunktion
function getX(obj) {
	return obj.x;
}

// führe funktion öfter aus,
// erzeugt Maschienencode
getX({ x: 4, y: 1 });
getX({ x: 7, y: 2 });
getX({ x: 1, y: 3 });
getX({ x: 1, y: 4 });

// hier muss deoptimiert werden
getX({ x: 1, z: 4 });\end{GenericCode}
\end{program}

In das Beispiel \ref{prog:js_deopt} zeigt, dass in Zeile 11 deoptimiert werden muss, da der Übergebene Typ nicht dieselbe Struktur besitzt, wie in den
vorhergehenden Aufrufen.

Aufgrund der hohen Verbreitung in quelloffenen und kommerziellen Projekten kann davon ausgegangen werden, dass, obwohl die Google V8-Engine

den anderen vorgezogen.

\subsection{Interpreter}

Aus diesem Baum wird im nächsten Schritt ein Bytecode generiert, der dann von dem Interpreter ausgeführt werden kann. Der Interpreter wird 
in der Google V8-Engine als \textit{Ingnition} bezeichnet und ist als Registermaschiene umgesetzt. Die meisten Bytecodes verwenden ein spezielles
Register mit dem Namen \textit{accumulator} um den zuletzt berechneten Wert zu speichern.

\begin{program}[h]
\caption{Bytecode der Funktion \textit{addiere}.}
\label{prog:d8_bytec}
\begin{GenericCode}
$ ./d8 --print-bytecode addiere.js
[generating bytecode for function: addiere]

Frame size 0
   16 E> 0x3a5e372c5ba @    0 : 91                StackCheck 
   26 S> 0x3a5e372c5bb @    1 : 1d 02             Ldar a1
   35 E> 0x3a5e372c5bd @    3 : 2b 03 00          Add a0, [0]
   39 S> 0x3a5e372c5c0 @    6 : 95                Return 
Constant pool (size = 0)

\end{GenericCode}
\end{program}

In der Ausgabe \ref{prog:d8_bytec} kann man erkennen, dass zwei weitere Register, a1 und a0 verwendet werden. Diese entsprechen den
Übergabeparametern auf dem Maschienstapel. Die einzelnen Bytecodes in \ref{prog:d8_bytec} können wie folgt Interpretiert werden:


\begin{itemize}
	\item StackCheck, Überpüft den Stapelzeiger auf validität.
	\item Ldar a1, Lädt den Wert von Register a1 in das \textit{accumulator} Register.
	\item Add a0, [0], Lädt a0 und Addiert es auf den Wert im \textit{accumulator} Register.
	\item Return Gibt die Kontrolle zurück an den Aufrufer. Der Rückgabewert ist jener des \textit{accumulator} Registers.
\end{itemize}


\subsection{Just-In-Time Compiler}

Diese Komponente wird in der Google V8-Engine als \textit{Turbofan} bezeichnet, da sie eine performantere Ausführung
von Codeabschnitten ermöglicht. Wird vom Interpreter erkannt, dass eine Funktion oft aufgerufen wird,
übergibt er den Bytecode an den Just-In-Time Compiler, damit dieser nativen Maschinencode erzeugt. Anschließend
wird dieses Kompilat für eine spätere Ausführung im Speicher abgelegt.
Dies kann mitmithilfe der d8-Konsole über die \textit{\%OptimizeFunctionOnNextCall()} Laufzeitanweisung simuliert werden. 
Damit solche Anweisungen von der Entwicklerkonsole interpretiert werden, muss sie mit dem Parameter \textit{--allow-natives-syntax} 
gestartete werden.

\begin{program}[h]
\caption{Optimierung und Deoptimierung.}
\label{prog:d8_optdeopt}
\begin{GenericCode}
function addiere(a, b) {
	return a + b;
}

addiere(1, 2);
// Optimiere funktion und speichere 
// sie im Cache
%OptimizeFunctionOnNextCall(addiere);
addiere(1, 2); // optimierter Aufruf
// 47.11 Falscher Typ -> deoptimiere
addiere(47.11, 2);	
\end{GenericCode}
\end{program}

\section{C++-Programmierschnittstelle}

Nachdem im nun bekannt ist, wie der Javascript-Code ausgeführt wird, widmet sich dieses Kapitel der C++-Programmierschnittstelle.
Es werden die wichtigsten Konzepte erklärt und mithilfe eines Beispielprogrammes veranschaulicht. Dazu wird Bezug auf die Quellen 
\cite{learnV8}, \cite{v8embed} und \cite{v8mem} genommen.

\subsection{Isolates}

Als \textit{Isolate} bezeichnet man eine unabhängige Kopie der V8 Laufzeitumgebung, die einen eigenen Speicherbereich verwaltet.
Ein Prozess kann mehrere dieser Objekte Instanziieren, aber jedes darf nur von jeweils einem Thread verwendet werden. 
Zu diesem Zweck muss mithilfe von Objekten des Datentyps \textit{Locker} aus der V8-Programmierschnittstelle ein mehrfacher Zugriff verhindert 
werden. Diese funktionieren wie eine Mutal-Exclusion und blockieren einen zweiten Thread, bis der erste den geschützten Bereich
verlassen hat.

\subsection{Contexts}

Ein \textit{Context} ist eine Ausführungsumgebung, die es ermöglicht, separaten, unabhängigen Javascript-Code in einer 
V8 Laufzeitumgebung (\textit{Isolate}) auszuführen. Da ein \textit{Isolate} Objekt mehrere Context-Ausführungsumgebungen besitzen kann, 
muss jene, die zur Ausführung verwendet werden soll, explizit angegeben werden. Dies wird mithilfe des RAII-Konzeptes 
(Ressourcenbelegung ist Initialisierung) durch Erstellen eigener Objekte des Types \textit{Context::Scope} erreicht.

	\centering \includegraphics[width=0.7\textwidth]{contexts}
	\caption{In dieser Illustration wird die Unabhängigkeit der verschiedenen Contexts zueinander veranschaulicht \cite{v8Context}.}
	\label{fig:contexts}
\end{figure}

In Abbildung \ref{fig:contexts} ist ersichtlich, wie mehrere Ausführungsumgebung verschachtelt aufgerufen werden können ohne sich 
gegenseitig zu beeinflussen. Nach Aufrufen des Destruktors von dem scopeB Objekt, wird die Ausführung in contextA fortgesetzt. 

\subsection{Speicherverwaltung}

Der Speicher innerhalb eines Isolate wird von einem Garbage-Collector verwaltet. Damit dieser weiß, welche Speicherbereiche
noch in Verwendung sind und welche nicht, werden Objekte über sogenannte Handles überwacht. Diese halten eine Referenz auf 
die Position eines Javascript-Objekts in dem von einem Isolate verwalteten Speicherbereich. Gibt es kein Handle mehr, dass 
ein bestimmtes Objekt referenziert, kann dieses durch den Garbage-Collector freigegeben werden. Hier
wird zwischen zwei Typen unterschieden:

\begin{figure}[h]
	\centering \includegraphics[width=1\textwidth]{handles}
	\caption{Speicherverwaltung mithilfe von Handles.\cite{v8Handles}}

\subsubsection{Local}

Ob ein Objekt noch valide ist oder nicht, wird hier mithilfe des RAII-Konzeptes (Ressourcenbelegung ist Initialisierung) ermittelt.
Dazu muss, bevor das erzeugen von Javascript-Objekten möglich ist, wie in Abbildung \ref{fig:handles} gezeigt, ein HandleScope Objekt auf dem C++-Stack allokiert werden. 
Dieses Objekt stellt einen eigenen Stack für Local-Handles zur Verfügung.
Wird es zerstört, zum Beispiel beim Verlassen des Scopes, werden alle Handles dieses HandleScope-Stacks gelöscht.

\subsubsection{Persitent}

Die Lebenszeit eines Persitent-Handles ist nicht an den aktuellen Scope gebunden. Daher muss man dem V8-Garbage-Collector selber signalisieren,
wenn es nicht mehr gebraucht wird. Dazu kann die \textit{SetWeak()} Funktion des Handle Objekts aufgerufen werden. Dieser Mechanismus ist hilfreich,
wenn ein Javascript-Objekt in mehreren C++-Funktionen verwendet werden soll.

\subsection{Anpassen von Javascript-Ausführungsumgebungen über das Global-Objekt}

Beim erstellen eines neuen V8-Contexts kann ein Objekt des Datentyps \textit{ObjectTemplate} angegeben werden, dass die Ausführungsumgebung des Contexts beschreibt.
Diesem Objekt kann man beliebig viele eigene Funktionen (\textit{FunctionTemplate} Objekte) oder Variablen zuweisen. Über \textit{FunctionTemplate} Objekte ist es wiederum möglich, C++ Funktionen aufzurufen. 
Dadurch lässt sich die Javascriptsprache beliebig erweitern.

\subsection{Das DebugInspector Protokoll}

Die Google-V8-Engine besitzt erweiterte Funktionen zur Fehlersuche über ein JSON basierendes Protokoll \cite{v8Debug}. Die in den Webbrowsern Google Chrome und Microsoft
Edge enthaltenen Entwicklerwerkzeuge unterstützen dieses und erlauben entfernten Zugriff auf V8-Instanzen via Websockets. 
Implementiert man die entsprechenden Interface-Klassen \textit{V8InspectorClient} und \textit{V8Inspector::Channel}
der V8-Programmierschnittstelle, damit sie Befehle über einen Websocket-Server erhalten können, ist es möglich, den von der Engine ausgeführten Javascript-Code mithilfe 
einer der zwei zuvor genannten Browser zu analysieren. Die \textit{V8InspectorClient} Implementierung muss die Verbindung zu einem \textit{Context} herstellen.
Danach können über den Websocket-Server erhaltene JSON-Befehle an die V8-Engine weitergegeben werden. Die \textit{V8Inspector::Channel} 
Umsetzung erhält die Antworten auf die Befehle und muss sie an den Befehlsgeber zurücksenden. Somit ist es möglich die Laufzeit eines laufenden Javascript-Codes zu 
analysieren und manipulieren. Außerdem kann man einzelne Funktionsaufrufe und Codesequenzen über die von den Browser-Entwicklerwerkzeugen zur Verfügung gestellte REPL (Read-eval-print loop) 
Konsole testen \cite{repl}.

Am Anfang des Beispiels kann man erkennen, dass ein HandleScope angelegt wird um alle Local Handles verwalten zu können. Hier wird keine Context::Scope

geworfen. Diese kann im Skriptquellcode mithilfe von \textit{try}-\textit{catch}-Blöcken gefangen werden. Diese Funktion kann nun innerhalb eines Programmes
an die V8-Engine übergeben werden:

Das komplette Beispiel befindet sich als CMake \cite{cmake} Projekt auf der CD-ROM/DVD unter \textit{Thesis/prototype2} und kann mit folgenden Befehlen 
übersetzt werden. Zum übersetzten wird der \textit{SMF\_3P} Ordner benötigt, da dieser die Bibliotheken der Google-V8-Engine in Binärform beinhaltet. Alternativ können
diese auch mit den Skripten in Anhang \ref{app:v8build} erzeugt werden. Dieser Ordner befindet sich auch auf der CD-ROM/DVD. \\

SUSE Linux Enterprise 12.5:

\begin{GenericCode}
$ mkdir build
$ cd ./build
$ cmake .. -DSMF_3P=~/SMF_3P
$ cmake --build .
\end{GenericCode}

Windows 10:

\begin{GenericCode}
$ mkdir build
$ cd ./build
$ cmake .. -T v140 -A x64 -DSMF_3P=C:/SMF_3P
$ cmake --build .
\end{GenericCode}
