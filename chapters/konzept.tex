\section{Compiler}

Wichtig ist hier zu erwähnen, dass vonseiten des WinCC OA SCADA Produktes für die jeweilige Plattform bestimmte Compiler
vorgeschrieben sind, weil ansonsten aufgrund von etwaigen \textit{ABI (Application Binary Interface)} Inkompatibilitäten mit 
der Programmierschnittstelle keine korrekte Funktionsweise garantiert wird. Für Linux ist in der WinCC OA Dokumentation ein C++-Compiler der 
\textit{GNU Compiler Collection (GCC)} in der Version 4.8.5 vorgeschrieben. Zum erzeugen von Windows Binärdateien wird der Compiler
des \textit{Visual Studio Toolset} in der Version v140 angegeben. Alle Programmkomponenten und Drittbibliotheken müssen mit diesen
Compilern gebaut werden.

\section{Linken der Google V8-Engine}

Im folgenden Abschnitt wird erklärt, wie ein Programm mit externen Bibliotheken umgehen kann. Die verschiedenen Möglichkeiten
werden dann abgewogen und in einem Fazit wird entschieden, welche Methode zum linken der Google V8-Engine verwendet wird.

\subsection{Statisches Linken}

Wird eine Bibliothek statisch gelinkt, dann werden die Funktionen dieser Bibliothek direkt in die ausführbare Datei kopiert.
Voraussetzung dafür ist, dass die gelinkte Bibliothek selbst statisch ist. Dies bedeutet, dass mindestens eine Objektdatei mit Hilfe des
Kommandozeilenprogrammes \textit{ar (archiver utility)} in ein Archiv umgewandelt wurde. \textit{Ar} fügt zu einem solchen Archiv eine 
Tabelle hinzu, in der vermerkt ist welche Symbole, wo im Archiv zu finden sind \cite{staticLinking}.

\subsection{Dynamisches Linken}

Beim dynamischen Linken werden die Funktionen einer dynamische Bibliothek in der ausführbaren Datei nur referenziert. Die dynamische
Bibliothek wird erst dann geladen, wenn das Programm gestartet wird. Ein wesentlicher Vorteil von dynamischen Bibliotheken gegenüber statischen
ist, dass der ausführbare Code für alle Prozesse, die diese Bibliothek benutzen nur einmal in den Speicher geladen wird \cite{dynLinking}.

\subsection{Fazit}

Da der Agent nur als einzelner Prozess laufen soll, ist durch die Verwendung von dynamischen Bibliotheken kein wirklicher Vorteil gegeben.
Es macht daher mehr Sinn die Bibliotheken der Google V8-Engine statisch in die ausführbare Datei zu linken, da man somit von externen Bibliotheken
unabhängig bleibt.

\section{Umsetzungskonzept}

Im letzten Abschnitt wurde erörtert, wie die V8-Bibliothek als externes Modul in die eigene Komponente
eingebunden werden soll. Nun wird die Art der Umsetzung diskutiert. Es wird hier vor allem auf die Anforderung der Wiederverwendbarkeit
acht genommen. 

\subsection{Dynamische Bibliothek}

Die Umsetzung als dynamische Bibliothek wäre praktikabel, da dies ein einfaches Aktualisieren der Komponente ermöglichen kann.
Wenn Teile der Implementierung aufgrund etwaiger Schwachstellen oder neuen Funktionen geändert werden, muss bei den Kundinnen und Kunden 
nicht jedes Programm, das die V8-Engine verwendet, einzeln aktualisiert werden, sondern nur die dynamische Bibliothek. Voraussetzung dafür
ist, dass die Schnittstellen nicht geändert werden.

\subsection{Statische Bibliothek}

Kapselt man die Funktionalität innerhalb einer statischen Bibliothek, so erhält jede ausführbare Datei eine eigene Instanz. Dies bietet keine
besonderen Vor- oder Nachteile.

\subsection{Ausführbare Datei}

Wird die komplette Funktionalität direkt innerhalb einer ausführbaren Datei umgesetzt, ist das Realisieren der Wiederverwendbarkeit nur schwer möglich.
Eine Option wäre, die Ausführung von Javascriptdateien über eine RPC-Schnittstelle (Remote Procedure Call) zu ermöglichen. Solch Schnittstelle
zu implementieren würde jedoch einen unnötigen Mehraufwand verursachen. Außerdem besteht die Gefahr, dass der Prozess überlastet wird,
wenn mehrere Teilnehmer gleichzeitig Zugriff auf die Schnittstelle verlangen.

\subsection{Fazit}

Die Umsetzung als ausführbare Datei mit einer RPC-Schnittstelle kann aufgrund der erläuterten Probleme als unpraktikabel angesehen werden 
und wird daher nicht in Betracht gezogen. Eine Implementierung als dynamische Bibliothek setzt voraus, dass sich die Schnittstellen nicht ändert,
was die Flexibilität in der Entwicklung neuer Funktionalitäten einschränken kann. Deshalb wird für die zu entwickelnde Programmkomponente 
das Erstellen einer statischen Bibliothek als Umsetzungskonzept gewählt. Diese soll dann innerhalb eines eigenen Agenten verwendet werden,
um die Ausführung von Javascriptdateien zu ermöglichen.

\section{Handbuch für Integratorinnen und Integratoren}

Javascript besitzt als Programmiersprache keine Typsicherheit, aus diesem Grund ist sie in größeren Codebasen nicht
immer einfach zu handhaben. TypeScript bietet hier Abhilfe, da es ein typsicheres Programmieren von Javascript-Code
ermöglicht. TypeScript-Quellcode kann dann durch einen TypeScript-Compiler in Javascript-Quellcode übersetzt werden.
Damit man die innerhalb des V8-Agenten implementierten Funktionen innerhalb dieser Programmiersprache verwenden kann, müssen somit
eigene Funktionsdeklarationen geschrieben werden. Um ein interaktives Handbuch für Systemintegratorinnen und Systemintegratoren
zu erhalten, bietet sich hier die Literate Programming Methodik an \cite{LiterateProgramming}. Die Idee ist es, die Funktionsdeklarationen
direkt im Quellcode mit Hilfe von speziellen Quellcodekommentaren zu erklären. Später kann dann aus dem Programmcode und diesen 
Kommentaren ein Dokument erzeugt werden. Das de facto Standard Programm zum Generieren solcher Dokumentationen, \textit{Doxygen},
unterstützt TypeScript und Javascript nur eingeschränkt \cite{DoxyGen}. Eine Alternative bietet daher \textit{TypeDoc} \cite{typedoc}.

\subsection{TypeDoc}

\textit{TypeDoc} ist ein Programm zum Generieren von Dokumentationen aus einem TypeScript-Programmquellcode.
Es ist möglich mit Hilfe von definierten Steuerbefehlen in den Kommentarblöcken Schnittstellen und Klassen zu beschreiben.
Folgendes Beispiel soll zeigen, wie dies auszusehen hat:

\begin{program}[h]
\caption{TypeDoc Beispiel.}
\label{src:typedoc}
\begin{GenericCode}
/**
* Returns the value stored within an datapoint element.
* @param dpe Datapoint element to get the value from.
* @returns The value stored within an datapoint element.
* Returned variable type depends on the datapoint element type.
*
* ### Basic usage example: 
* 
* ```ts
* var text = DpGet("System1:Example.text:_online_value");
* console.log(text); // :_online_value of System1:Example.text
* ```
*/
declare function DpGet(dpe: string): any;
\end{GenericCode}
\end{program}

Wie in \ref{src:typedoc} ersichtlich, werden über die Anweisungen \textit{@param} und \textit{@return} die Funktionsparameter und der Rückgabewert dokumentiert. 
Außerdem kann beschreibender Beispielcode direkt bei der Funktionsdeklaration eingefügt werden. 

\begin{figure}[h]
	\centering \includegraphics[width=1\textwidth]{typedoc}
	\caption{Generierte Dokumentation für \textit{DpGet}.}
	\label{fig:typedoc}
\end{figure}

In der Abbildung \ref{fig:typedoc} ist die von \textit{TypeDoc} erzeugte Dokumentation veranschaulicht. Parameter und Rückgabewert sind optisch hervorgehoben 
dargestellt und der Beispielquellcode wird mit Syntaxhervorhebung angezeigt.

\subsection{Fazit}

\textit{TypeDoc} bietet eine gute Alternative zu \textit{Doxygen} und wird deshalb für die Umsetzung des interaktiven Nachschlagewerks 
gewählt.

\section{Konzeptioneller Beweis}

Bevor mit der Implementierung eines eigenen Agenten gestartet wird, ist es zunächst sinnvoll, die Machbarkeit anhand einer einfachen konzeptionellen 
Umsetzung festzustellen. Dazu werden die aus den Beispielen \ref{cha:scada_code} und \ref{cha:v8_code} gewonnenen Erkenntnisse in einem eigenen Prototypen kombiniert. 
Das Ziel ist es die \textit{dpConnect} Funktion der WinCC OA C++-Programmierschnittstelle an die Google V8 Javascriptengine anzubinden.
Dazu muss zunächst eine eigene Observer-Klasse implementiert werden, die beim Erhalt von Datenpunkt-Wertänderungen eine Javascript 
Funktion aufrufen kann. Die aus den vorherigen Beispielen wiederverwendete Klassen und Funktionen sind hier nicht mehr aufgeführt.

In Javascript ist es möglich über die \textit{.bind} Anweisung einer Funktion einen eigenen Scope zuzuweisen. Dies wird in Zeile 38 geprüft und in dem Fall, dass
ein Funktionsscope gesetzt wurde, wird dieser für den Aufruf verwendet.

Auch diese Beispiel befindet sich als CMake \cite{cmake} Projekt auf der CD-ROM/DVD und ist unter \textit{Thesis/prototype3} zu finden. Es kann mit folgenden Befehlen 
übersetzt werden. Dazu wird das \textit{SMF\_3P} Verzeichnis benötigt und eine WinCC OA Installation benötigt. \\

SUSE Linux Enterprise 12.5:

\begin{GenericCode}
$ mkdir build
$ cd ./build
$ cmake .. -DSMF_3P=~/SMF_3P -DWINCCOA_INSTALL=C:/Siemens/Automation/WinCC_OA/3.16
$ cmake --build .
\end{GenericCode}

Windows 10:

\begin{GenericCode}
$ mkdir build
$ cd ./build
$ cmake .. -T v140 -A x64 -DSMF_3P=C:/SMF_3P -DWINCCOA_INSTALL=C:/Siemens/Automation/WinCC_OA/3.16
$ cmake --build .
\end{GenericCode}
